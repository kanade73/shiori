# PR にテスト追加 & レビュー

## 前提（このプロジェクトの開発フロー）

- 2人開発。相方はテストを書かない。**テストとレビューはこちらの責務**
- 相方のPRは「やりたいことの最小実装」として読む。テストがないのは欠陥ではなく分業
- テストは相方のコードを縛るためでなく、**推察した意図を固定して、レビューの根拠にする**ために書く
- ハッカソン3日。細かい指摘より「壊れているか」「企画の制約を破っていないか」を優先する

## 手順

### 1. PR を取得して意図を推察する

```bash
gh pr view <arg> --json number,title,body,headRefName,baseRefName,files
gh pr diff <arg>
gh pr checkout <arg>
```

diff とタイトル・本文から、**相方が何をしたかったか**を1〜3文で言語化する。実装ではなく目的を書く。
diff だけで意図が読めない箇所は、断定せず「〜と読んだ」と書き、レビューでも同じ表現で相方に確認を求める。

必ず AGENTS.md の制約に照らす。特に:

- 作品名・キャラ名（`hxh`, `momotaro`, 特定キャラ）が `data/` 以外のコードに条件分岐として現れていないか
- `NEXT_PUBLIC_` に API キーが載っていないか、LLM 呼び出しがクライアント側に出ていないか
- 検証層が「飛躍は通す・捏造は落とす」の境界を守っているか（存在しないエンティティを落とし、因果の捏造は通す）
- 生成前に嘘の型でモデルを誘導していないか（型判定は生成後）
- 先回りの抽象化（プラグイン機構など）を入れていないか

### 2. テスト基盤がなければ作る（初回のみ）

`vitest` が `package.json` の devDependencies になければ導入する。

```bash
npm i -D vitest @vitejs/plugin-react jsdom @testing-library/react @testing-library/jest-dom
```

- `package.json` の scripts に `"test": "vitest run"` を足す
- `vitest.config.ts` を作る。`lib/` は node 環境、`components/` と `app/` は jsdom
- テストファイルは対象の隣に `*.test.ts` / `*.test.tsx` として置く
- 基盤の導入は**テストとは別コミット**にする

### 3. テストを書く

対象は PR で変更・追加された振る舞い。実装の内部ではなく、**推察した意図が満たされているか**を検証する。

書く優先順位:

1. 意図の中心となる振る舞い（正常系1〜2本）
2. 企画の制約に関わる境界（例: 検証層が未知エンティティを落とすこと、既知エンティティ同士の飛躍は通すこと）
3. diff を読んで怪しいと感じた箇所を再現する失敗系

方針:

- LLM 呼び出し（`@ai-sdk/google`, `ai`）は必ずモックする。実 API を叩くテストは書かない
- カードデータは `data/` を読まず、テスト内に最小のフィクスチャを書く。**コードが作品を知らない**構造をテストでも守る
- 1テスト1主張。テスト名は日本語でよい。意図が読める名前にする
- 相方の実装に合わせて意図を歪めない。意図に対してテストを書き、実装が落ちるなら落ちたまま報告する

```bash
npm test
npx tsc --noEmit
npm run lint
```

### 4. テストの結果を分類する

- **通った**: 意図通り。レビューで「ここは確認済み」と書ける
- **落ちた・実装のバグ**: 修正案を出す。軽微（1〜数行）ならテストと同じコミットで直してよい。それ以上は相方に返す
- **落ちた・意図の読み違いかもしれない**: 直さない。テストは残し、レビューで「この読みで合っているか」を聞く

### 5. テストを PR ブランチに積む

```bash
git add <テストファイル と vitest 設定>
git commit -m "test: <PRの意図> のテストを追加"
git push
```

相方のブランチに直接 push する。相方の実装コミットは書き換えない（rebase・amend 禁止）。

### 6. レビューを PR に投稿する

日本語。相方向けなので短く、根拠はテストファイル名で示す。

```bash
gh pr review <number> --comment --body-file <レビュー本文>
```

必要なら `gh pr comment` で行単位ではなく PR 単位のコメントにまとめる。行コメントは3つを超えたら PR 本文側の箇条書きにする。

レビュー本文の構成:

```
## 読んだ意図
（1〜3文。「〜と読んだ」）

## 追加したテスト
- path/to/x.test.ts — 何を固定したか

## 結果
- 通った: ...
- 落ちた: ...（バグか、読み違いか）

## 指摘（重要度順）
1. **[壊れる]** ...
2. **[企画の制約]** ...
3. **[できれば]** ...

## 確認したいこと
- （意図が読めなかった箇所への質問）
```

重要度のラベル:

- **[壊れる]**: 動かない、例外、データ破壊。マージ前に直す
- **[企画の制約]**: AGENTS.md の「やらないこと」に抵触。マージ前に直す
- **[できれば]**: 可読性・重複。相方の時間があるときでよい。3つまで

最後に、マージしてよいかを一行で書く（「テスト通過・制約違反なし、マージ可」など）。

## やらないこと

- PR 全体を書き直さない。テストとレビューが成果物で、実装は相方のもの
- スタイルや命名の指摘を並べない。ハッカソンでは価値が低い
- カバレッジを目的にしない。意図と制約に関係ないテストは書かない
- 実 Gemini API を叩くテストを書かない
- 相方のコミットを rebase / amend / force-push しない
