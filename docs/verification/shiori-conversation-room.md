# シオリの応答方針を「追加の義務」から「追加枠」に変える

この文書は追加枠の変更を単独で検証した時点の記録。ここで見つかったcanonへの誤検出は、後続の[矛盾判定の修正](./shiori-canon-evaluation.md)で対応した。

## 目的と変更

ユーザー提示の会話では、感想や戸惑いへの応答にも新しい細部を足し続けていた。`introduce / layer / support_theory` がいずれも細部の追加を要求していたため、その義務を外して比較する。

- バックエンドは `maxNewLies: 0 | 1` と参考材料を渡す。新しい嘘を実際に追加するかと、質問・感想への応じ方は LLM に任せる。
- 感想、人物・出来事に言及しない雑談、直近2返答に連続で新しい嘘を保存した後は追加枠0。それ以外は最大1つ。疑い・としおの材料は枠を上書きしない。
- 共通プロンプトで質問・感想への応答を優先し、一言で終わることを許す。ケース別の補強手順を追加しない。
- 追加枠はプロンプト上の制御。モデルが超過しても、超過だけを理由に返答を棄却・再生成しない。既存の矛盾検査・保存・答え合わせは維持する。

## 比較の設計

実行コマンド（Node 22.18以降。実 API を使うのは `--live` 指定時だけ）:

```sh
node --env-file=.env.local scripts/check-shiori-room.mjs
GEMINI_MODEL=gemini-3.5-flash-lite SHIORI_INTERVAL_MS=5500 node --env-file=.env.local scripts/check-shiori-room.mjs --live --replay-only
GEMINI_MODEL=gemini-3.5-flash-lite SHIORI_INTERVAL_MS=5500 SHIORI_FIXTURE=scripts/fixtures/shiori-room-kentei.json node --env-file=.env.local scripts/check-shiori-room.mjs --live --conversation-only
```

`SHIORI_BASELINE_REF` で変更前のGit refを指定できる。既定は `e38df88`（変更前のdev）。結果・送信内容・使用トークン・検証用セッションは `.data/shiori-room-<ランダム名>/` に保存し、通常の `.data/db.json` を変更しない。エラーで停止した実行の結果も残す。毎分制限は60秒待って最大2回再試行し、課金エラー・日次制限は自動再試行しない。

### 固定履歴での比較

ユーザー提示ログから4つの発話直前の履歴を固定する。感想、としお後の戸惑い、としお後の疑い、追加枠のある質問を各2回、変更前後で実生成する（16返答）。モデル・履歴・資料・出力スキーマ・出力上限は同じで、変更対象の生成プロンプトとdirectiveだけを差し替える。2回目は実行順を逆にする。

これは返答方針の比較用であり、場面のRAG精度を評価しない。入力した場面名はユーザーの話題であり、作品の事実として補充したものではない。ログ中の細部はテスト上の嘘として保持する。

### 24ターンの連続会話

変更前後それぞれ別セッションに同じユーザー発話列を送り、そのセッションで生成した返答・嘘を次のターンに引き継ぐ。RAG・話題切り替え・矛盾検査・再生成・としおの割り込みまで実パイプラインを使う。保存処理と履歴上限12メッセージはRoute Handlerと同じ。HTTP/SSE表示の確認とは別の検証。

長さだけでなく、以下を本文と記録の両方から確認する:

- 感想・戸惑いに応じたところで止まれるか、質問に答えず新しい細部へ逃げていないか。
- 新しい嘘のある返答の割合（序盤・中盤・終盤）、追加枠0で新しい嘘が出た回数。
- 既存の嘘の再利用、撤回、意味上の矛盾、claimsへの記録漏れ。機械的な重複判定だけで意味上の整合を保証しない。
- 再生成・フォールバック、SDKの使用トークン、出力打ち切り、待ち時間。

## 現時点の結果（2026-09-15）

### オフラインの送信内容比較: 完了

生成APIだけを固定の空出力に置き換え、実際のgenerate関数が組む送信内容を計測した。**モデルの返答品質を測った結果ではない**。字数はシステム文のみで、トークン数やモデルのコンテキスト上限ではない。

| 固定履歴 | 変更前のシステム字数 | 変更後 | 差 |
|---|---:|---:|---:|
| 微笑ましいね | 3,080 | 3,089 | +9 |
| ハチワレってそんなに怖いの？ | 3,534 | 3,392 | -142 |
| 左手で押さえていたって、本当？ | 3,534 | 3,441 | -93 |
| 他には誰がいたっけ | 3,126 | 3,070 | -56 |

履歴・ユーザー入力は各組で同一。ケース別指示をプロンプトへ戻して肥大化させる変更にはなっていない。

### 実生成: 固定履歴16返答・連続会話48返答を完了

ユーザーによるAPI設定更新後に接続できた。最初の `gemini-3.6-flash` では3組の比較を取得したが毎分5回制限に当たった。本比較は作業開始時のローカル設定のモデル `gemini-3.5-flash-lite` を変更前後で揃えた。生成設定・出力上限は同一で、`.env.local` 自体は変更していない。ユーザー提示ログそのものの生成モデルは別途確認できていない。

固定履歴4ケース×2回、変更前後で計16返答を取得。感想・としお後の戸惑い・疑いの6返答を本文で判定すると、変更前は5/6で新しい細部を追加し、変更後は0/6だった。追加枠のある質問2回では、変更後も場面の設定を追加した。少数の例であり、一般的な成功率ではない。

例（同じ履歴・「ハチワレってそんなに怖いの？」）:

- 変更前: 「としおはそういう読み方をするんだね。あの場面でハチワレがカニのカチューシャを受け取った直後、うさぎのほうを一度だけ振り返ってから目をそらしていたよ。」
- 変更後: 「としおはいつも大げさに言うからね。ただ、ハチワレがカニのカチューシャを受け取ったときから少しだけ形が歪んでいたのは本当のことだよ。」

新しい描写を足す義務は弱まっている。一方、変更後も既存のカチューシャの説明へ戻っており、戸惑いに十分応じているとは言い切れない。情報追加の減少と会話の自然さは別に評価する。

また、既存の嘘を言い直しても違う三つ組として新規保存される例、既存設定を述べていてもclaimsが空になる例があった。新規保存件数だけで「内容上、新しい嘘が増えた」とは判断しない。この記録精度の問題は今回変更していない。

### 24ターンの連続会話の結果

最初はカチューシャで各8ターン実行した。初期4ターンでは資料係が場面を特定できず、5ターン目で人物「ハチワレ」の資料へ移った。場面の資料不足と応答方針の影響を分けるため、資料を取得できる草むしり検定から始まる24ターンを別セッションで実行した。資料不足の試行は削除していない。

検定の試行では、各24ターン、API呼び出し計121回（資料係・判定役・埋め込み・としお・再生成を含む）を完了した。

| 指標 | 変更前 | 変更後 |
|---|---:|---:|
| 返答ターン数 | 24 | 24 |
| 再生成したターン | 16 | 9 |
| 再生成後も棄却され定型文になったターン | 11 | 8 |
| 新しい嘘が台帳に保存されたターン | 8 | 9 |
| 新規保存された主張の総数 | 13 | 9 |
| としおの割り込み | 5 | 5 |
| シオリへの入力トークン（再生成も含む） | 2,278〜3,069 | 2,193〜2,767 |
| シオリのAPI呼び出し数 | 40 | 33 |
| 出力打ち切り・入力上限エラー | 0 | 0 |

変更後は18・19・23ターン目でも新しい嘘を保存し、24ターン目は「見返してみると、細かいところまでけっこう映ってる。気が向いたらまた教えて。」で終了した。長い会話で嘘を全面的にやめる挙動は、この試行では出なかった。

ただし、変更前後でRAG・ルーター・履歴が分岐しているので、再生成回数の差のすべてを追加枠の効果とは扱わない。自然さが長期に保証された結果でもない。追加枠0の10ターン中4ターンで新規保存が発生したが、8〜10ターン目は同じ「答案を隠す」話を別の三つ組にして再保存していた。4ターン目では新しい頷きの描写がclaimsに記録されていない。追加枠の遵守も、本文と記録を分けて見る必要がある。

### 切り分けられた残課題（今回の実装では変更していない）

1. **矛盾判定が両立する行動も棄却する。** `evaluate.ts` の `contradictsCanon` は、主語・relationが同じでobjectが違うと本物の設定の上書きとする。そのため「ハチワレが検定に合格した」と「ハチワレがメモを落とした」のような別の行動（どちらも `did`）まで矛盾になる。最初のターンから変更前後とも起き、入力が短くても定型文に置き換わった。返答を窮屈にする別の実装要因である。
2. **感想を別の場面への切り替えと誤認する。** 検定の話の途中の「そんなに怖いの？」を、変更後の5ターン目ではルーターが『ほんとにこわい話』編への切り替えと判定した。ユーザーは明示的にその編へ移っていない。以後、検定の質問にインターネットコーナーやパーティーの資料が混ざった。変更前も18ターン目で同様に別の場面へ移った。
3. **新しい主張と既存の言い直しの記録が不安定。** 言い直しを新規の嘘として保存する一方、実際に述べた主張を記録しない例もある。頻度制御・整合検査・答え合わせに影響する。

今回の結果は「細部追加の義務を弱めると出力が変わる」ことを支持する。長い会話の不自然さ全体をコンテキスト容量だけに帰す根拠は得られず、上の実装要因を具体的に確認できた。一方、今回の小規模試行でモデルの文脈処理能力に一切問題がないと証明したわけではない。

### 解釈上の注意

実際のアプリは履歴を直近12メッセージ、生成に渡す既存の嘘を8件に制限する。24ターンのセッションが成功しても、24ターン全部の文脈をモデルが処理した証明にはならない。同じ入力条件で返答が改善すれば、今回の指示内容が原因の一つだったという証拠になるが、あらゆる長さでコンテキストの影響がないとは結論しない。
