# そんなシーンあった？
**「作品を見る前に戻って、もう1回楽しみたい」**

誰もが一度考えますが、実際には時間を巻き戻すことはできません。
しかし、そのような要望に対して私たちdevくまは時間を戻すのではなく記憶を戻すということを提案します。

## ターゲット
- アニメを1周最後まで視聴したが、記憶を消して何度も見たいと考えている人

## アイデア
ある日インターンでコードを書いていてQwen3.6-27Bの言う通りにgitのコマンドを打ったところ、半日書いたコードが全て消えました。そこで「午前中の時間全部無駄じゃん…」と思いました。
そのとき、自分が戻したいのは時間もしくはコードであるということを思いつきました。（どちらかがあれば同じ成果に戻せる）
**つまり、ここでいう戻したいはずだった時間とは、コードの差分のことだったのです。**
そこで時間を戻りたい日常の場面について考えると、アニメなどの作品を時間を戻してもう一度初めてのつもりで見たいと考えたことを思い出しました。
ここでは先ほどの例同様に、**記憶の差分=時間の差分**と見ても差し支えないと考えたのです。

## アプリ紹介
このアプリでは、登場するキャラクター「シオリ」と「としお」との対話を通じて1周目に視聴したアニメの記憶にノイズを混ぜ、知っているはずのアニメを少しだけ未知に戻します。
会話の後に実際に2周目として見直すと、「そんなシーンあった？」という新しい視点からアニメを見ることができたり、シオリやとしおとの会話によって忘れてしまったシーンをもう一度初めての気持ちで楽しんだりすることができるようになります。

![image](https://ptera-publish.topaz.dev/project/01M2J2AS0F05TF3W2NG2ZE6JA1.png)

視聴後は答え合わせ機能を用意しているため、セッションでシオリやとしおとの会話の中でどこが嘘でどこが本当だったか確認することも可能。

## 使用技術

### 構成
| 層 | 選定 |
|---|---|
| フロント | Next.js (App Router) / React / TypeScript / TailwindCSS |
| バックエンド | Next.js Route Handlers（別サーバーなし） |
| LLM | Gemini API（生成・埋め込み・構造化出力） |
| 検索 | Wikipedia (MediaWiki API) + 文字 bigram + ベクトル検索 |
| Vector DB | sqlite-vec（SQLite 組み込み） |
| 永続化 | JSON ファイル + SQLite |
| デプロイ | Docker / Fly.io（永続ボリューム） |
| テスト | Vitest / Testing Library（約 245 件） |

### アピールしたい技術・工夫

会話は「話題を特定する → シオリが答える → 嘘を検査する → としおが乗る → 最後に答え合わせ」の順に流れます。その順に、頑張ったところを並べます。

**1. 話数を聞かない RAG（Wikipedia × ハイブリッド検索）**
「何話まで見た？」とは聞きません。「牢屋のとこ」「大きい敵を倒しに行く話」のような一言から Wikipedia の記事を検索し、いま話している場面を特定します。文字 bigram（固有名詞に強い）とベクトル検索（言い換えに強い）の2本立てで、Reciprocal Rank Fusion で順位を混ぜています。

**2. 組み込み型 Vector DB（sqlite-vec）**
別サーバーを立てず、SQLite に sqlite-vec を読み込んで段落の埋め込みと近傍探索を1ファイルで済ませます。埋め込み API の無料枠（1分100件）に合わせて、段落は裏で80件ずつ1分おきに埋め込み、揃うまでは bigram だけで検索して会話を待たせません。

**3. 資料係の分離（ネタバレ境界）**
検索した段落は、シオリではなく「資料係」の LLM に渡して、場面の名前と事実だけを構造化出力で抜かせます。シオリの文脈には生の段落ではなく要約した事実（1話題あたり60トークン程度）しか入りません。場面が作品データの「編」に対応すれば、そこまでを視聴済みとみなし、それより先の設定はシオリに渡しません。

**4. 事実と嘘の分離（Structured Output × 知識グラフ）**
シオリは返答文と同時に、その文で述べた「設定上の主張」を主語・関係・目的語のトリプルとして返します。関係は閉じた語彙（identity / likes / did など）に限定し、本物の設定と嘘を同じ形で保存します。各主張には本物か作り話かの印と、本文中の該当箇所の引用が付きます。

**5. ルールベースの矛盾検出（Generate → Verify → Regenerate）**
「過去の嘘と矛盾していないか」「本物の設定を上書きしていないか」を LLM に聞き直すのではなく、コード側の決定的なルールで判定します（1主語1値の関係、likes/dislikes のような対の関係、同じトリプルの肯定と否定）。矛盾があれば理由を添えて1回だけ再生成し、それでも直らなければ濁した返答に差し替えます。**発想は LLM に任せ、整合だけを機械で縛る**のが設計の芯です。

**6. 嘘の記憶と表記ゆれの吸収**
作り話の主張は別名を正式名に正規化して保存し、次の発話から材料に含めます。セッション内で嘘が一貫し、シオリは自分の嘘を認めません。

**7. 2人目のキャラ「としお」（役割分担したマルチエージェント）**
シオリの返答のうち嘘の部分に印を付けてとしおに渡し、どこが嘘かを知ったうえで、否定せずに深い考察を重ねさせます。考察は、作り手の作風（Wikipedia から1回だけ抽出してキャッシュ）と、コードがランダムに選ぶ切り口（反転・伏線・都市伝説など）を土台に組みます。ユーザーがとしおの考察を疑うと、シオリがそれを支える細部をもう1つ足して整合を取ります。

**8. 話題の切り替わり検知と履歴の圧縮**
「そういえば〜」のような発話を、ゲート（API なし）→ 軽量モデルの判定役の2段で検知し、話題が変わったときだけ指示語を解いた検索クエリを組み直して RAG を引き直します。前の話題の履歴はシオリに渡さず、嘘だけを別経路で渡すので、コンテキストを小さく保ちながら矛盾検査は効き続けます。判定役はシオリと別モデルにして、無料枠のレート制限を分けています。

**9. 答え合わせ（アプリの外側からの種明かし）**
発話ごとに主張の真偽と引用位置を記録しているので、本文を本当/嘘で塗り分けて振り返れます。キャラの口からではなくアプリの外側から明かすので、「キャラは嘘を認めない」原則と両立します。

**10. 作品知識をコードから分離**
作品の設定・キャラ・場面・知識源は `data/<作品>/work.json` に置き、コードは作品名を一切知りません。ディレクトリを足せば作品が増えます。
