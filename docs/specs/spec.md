# 仕様書 — 考察ミスディレクションアプリ（仮）

> ハックツハッカソン提出物 / テーマ「時」
> 最終更新: 2026-09-14 / ステータス: ドラフト

---

## 1. コンセプト

### 1.1 解決したい欲望

「過去に戻って、初めての状態でもう一度アニメを見たい」

### 1.2 アプローチ

時間を巻き戻すことはできないので、**観測者側の記憶をミスディレクションする**。

2周目の視聴前に、キャラクターが「本当らしい嘘の考察」を語りかける。ユーザーはそれを半分信じた状態で本編を見返すことになり、既知の作品が少しだけ未知に戻る。

### 1.3 テーマ「時」への接続

時間そのものを操作するのではなく、時間に対する**認識**を操作する解き方を取る。

---

## 2. 体験フロー

```
起動
 → 作品選択（昔話 / HUNTER×HUNTER）
 → チャット画面
 → ユーザーが作品について質問・言及
 → キャラクターが考察を語る（嘘）
 → ユーザーが疑う / 根拠を求める
 → キャラクターが出典を提示して押し通す
```

想定利用シーンは、視聴前の数分。長時間の利用は前提にしない。

---

## 3. 画面仕様

### 3.1 作品選択画面

| 要素 | 内容 |
|---|---|
| 作品カード | 収録作品を一覧表示。2件 |
| 選択後 | チャット画面へ遷移 |

作品の追加UIは**設けない**（4.4 参照）。

### 3.2 チャット画面

| 要素 | 内容 |
|---|---|
| キャラクター表示 | ドット絵。メガネのラインが顔を横断する構図、ピンク配色 |
| メッセージリスト | 通常のチャットUI。応答はストリーミング |
| 入力欄 | テキスト入力 |
| 出典チップ | 応答に付随。タップで参照カードの内容を表示 |

**出典チップが本アプリの見せ場。** 嘘の考察に、実在するカードが出典として添えられる。ユーザーがタップすると元の事実が読めるが、キャラクターの解釈とは食い違っている。「嘘なのに出典はちゃんとある」という構図がそのままギャグになる。

## 4. 機能要件

### 4.1 考察生成（コア機能）

処理の順序:

1. **retrieval** — ユーザー発話から関連カードを検索（ベクトル + タグ）。上位N件を取得
2. **生成** — カードを材料としてLLMに考察を書かせる。飛躍を構造的に制約しない
3. **検証** — 生成結果を検証層に通す（4.2）
4. **型判定** — どの嘘の型になったかを事後分類（4.3）
5. **返却** — 応答本文 + 参照カードID + 型ラベル

**設計原則**: 事実は正確に、飛躍は自由に、捏造は落とす。

### 4.2 検証層

生成された考察が参照している人物・事物・出来事が、実在カードに存在するかを照合する。

| 判定 | 扱い |
|---|---|
| カードに存在する要素のみで構成 | 通す |
| 要素間に存在しない因果・関係を主張 | **通す**（これが嘘の本体） |
| カードに存在しない要素が登場 | 落として再生成 |

再生成は最大2回。それでも通らない場合は、より salience の高いカードに絞って再試行する。

### 4.3 嘘の型（事後分類）

| 型 | 内容 |
|---|---|
| 因果反転 | 助けた ↔ 助けられていた |
| 人物すり替え | 別の人物が本来その役だった |
| 動機差し替え | 善意 → 打算 |
| 時系列入れ替え | 前後関係の捏造 |
| ボツ案フレーム | 「初期案ではこうだった」 |
| 由来の後付け | 名前・呼称に意味を与える |
| 伏線型 | 後の展開が前の場面に効いていたと主張する |

**伏線型は2周目視聴という前提と最も噛み合う**（1周目では作れない嘘）。構造的にネタバレを含むが、2周目前提のため許容する。

分類は生成後に行う。生成前に型を指定してモデルを誘導しない。

判定の実装は当面LLMで行い、余力があれば小型エンコーダ（ModernBERT系の分類ヘッド）に置き換える。ラベルが作品非依存なので、置き換えても汎用性は損なわれない。

### 4.4 収録作品

| work | 内容 | 想定カード数 |
|---|---|---|
| 昔話1本 | パブリックドメイン。権利面の説明はこちらで行う | 20〜30 |
| HUNTER×HUNTER | 密度の説得力を担保 | 150〜300 |

**作品追加機能はアプリに実装しない。** 拡張性は「`data/` にJSONLを足せば動く」という構造で担保し、カード生成は `tools/` のPython CLIが担う。

この2作品が選ばれている理由は権利対策だけでなく、**構造も密度も大きく違う2つが同一コードで動く**ことが汎用性の実証になるため。

## 5. データ仕様

### 5.1 カード

1カード = 1主張。JSONL。

```jsonl
{"id":"hxh-112","work":"hxh","arc":"yorknew","type":"event","order":112,
 "claim":"クラピカは鎖を用いて旅団の一人を拘束した",
 "entities":["クラピカ","旅団"],
 "slots":{"手段":"鎖","対象":"旅団員"},
 "salience":4,"spoiler":3,"tags":["能力","対決"]}
```

| フィールド | 型 | 内容 |
|---|---|---|
| `id` | string | 一意 |
| `work` | string | 作品ID |
| `arc` | string | 章。昔話は `main`、章に属さない設定は `common` |
| `type` | enum | `setting` / `event` / `relation` / `term` |
| `order` | int | 作中の時系列。伏線型が使用 |
| `claim` | string | 主張1文 |
| `entities` | string[] | 登場要素。検証層と関係グラフ導出に使用 |
| `slots` | object | 歪曲の取っ手 |
| `salience` | int (1-5) | 知名度。高いほど嘘の土台として強い |
| `spoiler` | int (1-5) | ネタバレ度 |
| `tags` | string[] | 自由タグ |

**作品固有のスキーマは持たない。** グラフ構造は保存せず、必要なら `entities` の共起から導出する。

### 5.2 保存

SQLite / libSQL (Turso)。カード本体とベクトルを同一テーブルに持ち、`vector_top_k` で検索する。

### 5.3 カード生成（アプリ外）

`tools/generate_cards.py`。あらすじ等のテキストを入力し、カードJSONLを出力するCLI。

原文をそのまま写さず、事実を自分の言葉で1文に要約させる。確信度の低いカードは出力しない。

## 6. API

### `POST /api/chat`

Vercel AI SDK の `useChat` 互換。

**Request**

```json
{ "workId": "hxh", "messages": [{ "role": "user", "content": "..." }] }
```

**Response** — ストリーミング。本文に加えて以下を data として返す。

```json
{ "citedCardIds": ["hxh-112", "hxh-045"], "lieType": "伏線型" }
```

LLM呼び出しは Route Handler 内でのみ行う。APIキーはクライアントに出さない。

## 7. キャラクター仕様

| 項目 | 内容 |
|---|---|
| 外見 | ドット絵。メガネのラインが顔を横断する構図、ピンク配色 |
| 態度 | 自信満々。指摘されても訂正せず押し通す |
| 出典の扱い | 実在するカードを堂々と誤読して根拠にする |
| 知らない作品 | 「興味ないから知らない」と突っぱねる |

**押し通す態度が崩れると嘘の説得力ごと落ちる。** 汎用モデルは訂正に流れやすいため、プロンプトのみで維持できるかを早期に検証する。維持できない場合のみ、口調のLoRAを検討する（未決）。

## 8. 技術スタック

| 層 | 選定 |
|---|---|
| フロント | Next.js (App Router) + TypeScript |
| チャットUI | Vercel AI SDK (`useChat`) |

## 9. スコープ外

- 作品の追加・取り込みUI
- ユーザー認証、履歴の永続化
- オフライン動作（**撤回済み**。「見る時と見る気になる時は別」という判断）
- ローカルLLMによる推論のアプリ組み込み
- 章間の因果・依存関係の構造化（`order` の大小で足りる）

---

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| 出力の面白さがばらつき、デモでスベる | デモで使う想定問答を事前生成し、良い出力をキャッシュしておく |
| カードが薄く、考察がつまらない | カード作成を最優先で着手。実装と並行して進める |
| 口調がプロンプトで保てない | 初日に検証。崩れる場合のみLoRAを検討 |
| 当日ネットワークが不安定 | キャッシュ済み応答で最低限のデモが通るようにしておく |

---

## 11. 優先順位

**Must**（これが無いと企画が成立しない）

- 考察生成 → 検証 → 返却の一連
- カード2作品分
- チャットUI + キャラクター表示

**Should**

- 出典チップ（見せ場）
- 嘘の型の事後分類

**Could**

- 型ラベルによる口調の出し分け
- 分類器の小型エンコーダ化
- 口調LoRA
